# ADR-0013: 스키마 변경은 당분간 create_all과 열 추가 보정으로 처리한다

- 날짜: 2026-11-08
- 상태: 채택
- 작성: @PSHUN03 (BE-05, 담당 @1yuxnp 대신 진행) · 검토: @1yuxnp

## 배경
앱은 시작할 때 `Base.metadata.create_all`로 테이블을 만들고, 기존 테이블에 새로 생긴 nullable 열은 `add_missing_columns`(`app/db.py`)가 `ALTER TABLE ... ADD COLUMN`으로 붙인다. 11월에 주간 리포트, 거래내역, 사용량 기록 같은 테이블이 늘면서 Alembic 같은 마이그레이션 도구를 도입할지 정해야 했다 (BE-05).

지금까지의 스키마 변경은 모두 새 테이블 추가이거나 nullable 열 추가였다. 열 이름 변경, 타입 변경, NOT NULL 열 추가, 데이터 옮기기는 없었다.

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 지금 방식 유지 (create_all + 열 추가 보정) | 추가 의존성 없음, 배포 절차 그대로, 팀원이 새로 배울 것 없음 | 열 이름·타입 변경, NOT NULL 열, 데이터 이전을 처리하지 못함. 변경 이력이 코드에 남지 않음 |
| B. Alembic 도입 | 변경 이력과 되돌리기, 모든 종류의 변경 지원 | 마이그레이션 파일 작성·리뷰 부담, 배포 시 `alembic upgrade` 단계 추가, 기존 운영 DB를 기준점으로 맞추는 작업 필요 |

## 결정
A를 유지한다. 제출과 발표까지 남은 기간이 짧고, 예정된 변경도 새 테이블이나 nullable 열 추가뿐이라 A로 충분하다. 운영 DB(Render PostgreSQL 무료)는 2026-12-01에 만료되어 장기 운영 데이터도 없다.

## 결과
- 새 테이블과 nullable 열은 지금처럼 모델만 고치면 배포 때 반영된다.
- 아래 중 하나가 필요해지면 B(Alembic)를 도입하고 이 ADR을 대체한다.
  - 기존 열의 이름이나 타입을 바꿔야 할 때
  - 기존 테이블에 NOT NULL 열을 추가해야 할 때
  - 데이터를 옮기거나 변환해야 할 때
  - 프로젝트 이후에도 운영 DB를 계속 유지할 때
